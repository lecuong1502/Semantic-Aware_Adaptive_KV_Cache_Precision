\section{Introduction}
\label{sec:introduction}

Large language models are increasingly run on personal hardware, with tools such
as Ollama \cite{ollama} and llama.cpp \cite{llamacpp}, for privacy, for offline
use, and to avoid a per-token bill. That hardware is not doing only
one thing: a laptop also runs a browser with hardware acceleration, a video
player, an editor. Unlike a datacenter accelerator partitioned by MIG or MPS, a
consumer GPU offers no memory isolation between the processes that share it.
Video memory goes to whoever asks first, and no process is told when another
takes more. A generation session that fits comfortably can then fail outright
when another application grows: the session ends, and its cached context is
lost.

A language model's memory is not monolithic. Its weights are fixed for a session,
but its key-value cache grows with every token and can be held at varying
precision, trading fidelity for space. This paper asks whether that trade can be
made \textit{during} a session, in response to pressure the engine did not cause,
and whether the loss can be concentrated where it matters least: on the cached
positions the model's attention consults least.

Three research questions follow.
\begin{itemize}
\item \textbf{RQ1.} How volatile is available video memory on a consumer laptop
under realistic multitasking, and how does that volatility meet a session in
progress?
\item \textbf{RQ2.} Can a runtime that cooperates with no scheduler detect
pressure fast enough to act?
\item \textbf{RQ3.} Does allocating precision by semantic importance preserve
task-level quality better than allocating it uniformly, at equal average
compression?
\end{itemize}

The paper makes four contributions.
\begin{enumerate}
\item \textbf{A characterisation of video memory contention on a consumer
laptop.} It gives the size, speed and persistence of spikes, attributed to the
processes and actions that caused them. On the machine studied, everyday
applications take hundreds of MiB and mostly keep it
(Section~\ref{sec:contention}).
\item \textbf{A scheduler-agnostic pressure monitor,} whose thresholds are set by
a rule from that measurement. Against synthetic and replayed contention it
caught every RED episode it could, at a median latency of about 120\,ms, with no
false alarm (Section~\ref{sec:detection}).
\item \textbf{A semantic-aware precision allocation policy,} with a from-scratch
engine that implements it: a paged, mixed-precision key-value cache whose freed
memory returns to the driver.
\item \textbf{A task-stratified evaluation that isolates allocation from
compression,} holding average compression equal between uniform and
semantic-aware quantisation.
\end{enumerate}

\section{Background and Related Work}
\label{sec:background}
% TODO: the KV cache and its growth, and memory management on consumer GPUs,
% condensed from the thesis's Chapter 2.

Related work falls into four families. Each makes an assumption that does not
hold for a single user on a shared consumer GPU, and naming it is what locates
this work.

\paragraph{Adaptive serving under memory pressure.} FineServe
\cite{fineserve}, MorphServe \cite{morphserve}, Oneiros \cite{mirage} (first
released as MIRAGE) and eLLM \cite{ellm} adapt memory allocation at runtime and
show that such adaptation is worthwhile. Each assumes a dedicated accelerator, a
scheduler that sees the incoming work, and many concurrent requests across which
to trade. Their memory pressure comes from workload the system itself admits,
which is not so when the pressure comes from a browser.

\paragraph{Static cache quantisation.} KVQuant \cite{hooper2024kvquant}, KIVI
\cite{liu2024kivi} and KVTuner \cite{kvtuner} establish how far a key-value
cache can be compressed. They assign precision once, offline, and leave no lever
to pull when memory is taken away mid-session. This work uses their kind of
quantiser and replaces their allocation.

\paragraph{Attention-guided eviction.} H2O \cite{zhang2023h2o}, StreamingLLM
\cite{xiao2024streamingllm} and Ada-KV \cite{feng2024adakv} use attention
statistics to decide what to discard, showing that attention identifies the
cached content that matters. Eviction, however, is irreversible and driven by a
fixed budget, not by external pressure. This work reuses the signal and makes
the decision reversible.

\paragraph{Consumer and edge inference.} llama.cpp \cite{llamacpp}, PowerInfer
\cite{song2024powerinfer} and FlexGen \cite{sheng2023flexgen} target
constrained hardware and contribute substantial offloading and scheduling. They
treat memory capacity as fixed: a configuration that does not fit is refused or
offloaded before generation begins, and none adapts mid-session to contention
from another process.

No system in these families reallocates cache precision at runtime,
non-uniformly, in response to pressure it did not cause.

\section{Design}
\label{sec:design}

\subsection{Overview}
\label{sec:overview}

\textit{MicroInfer} keeps a generation session alive when another process on the
same consumer GPU takes video memory it did not expect to lose. It changes the
precision at which the key-value cache is held, page by page and while decoding
continues, and chooses which pages to degrade by how much attention the model
pays to them.

The solution has two layers. The \textbf{engine} runs the model over CUDA kernels
written for this work and holds the cache on \textit{pages}, the keys and values
of $P = 32$ consecutive positions of one layer, each at one of four
\textit{precision tiers}: FP16, INT8, INT4 or INT2. Pages come from the CUDA
virtual memory management interface \cite{cudavmm}, one address range per tier, so that memory
a smaller tier frees returns to the driver instead of staying with the engine.
The \textbf{control loop} decides, while the engine runs, which page is held at
which tier. It has four components (Figure~\ref{fig:overview}):
\begin{itemize}
\item a \textbf{VRAM pressure monitor}, which polls the driver's free memory on a
background thread and classifies it as GREEN, YELLOW or RED, with hysteresis;
\item an \textbf{attention importance scorer}, which keeps, for every page, an
exponentially weighted average of the attention mass on its positions;
\item a \textbf{precision controller}, which turns the pressure level, the
importance scores and the current tiers into a \textit{requantisation plan},
downgrading the least important pages under pressure and upgrading the most
important first once it passes; it contains no device code, so the policy can be
tested, and compared with a uniform one, in isolation;
\item a \textbf{paged mixed-precision cache manager}, which applies the plan by
requantising each page into a new one at its target tier and freeing the old.
\end{itemize}

A plan is applied only \textit{between} decoding steps, never inside a kernel
launch, so no kernel sees the cache half converted; attention reads each page at
its current tier, dequantising as it loads. Three properties hold throughout:
memory a downgrade frees reaches the driver, where both the process that needs it
and the measurement can see it; a tier belongs to a \textit{(layer, page)} pair,
not to a token position; and the recent context stays at FP16, both because the
page still being filled cannot be quantised --- a key channel's scale spans the
whole page --- and because a recency floor protects recent positions as a matter
of policy.

\subsection{The VRAM Pressure Monitor}
\label{sec:monitor}

The monitor answers one question for the rest of the loop: how close the machine
is to running out of video memory, whoever is taking it. It is a background
thread that polls the driver's free memory, the \textit{headroom}, every 50\,ms
through NVML \cite{nvml}. Its polls keep absolute deadlines, so that a slow reading delays
only itself. The engine releases the Python interpreter lock while the device
works, so the thread keeps its schedule beside decoding and prefill alike.

\paragraph{Levels.} Headroom is classified by two thresholds in MiB, not in
percent, because contention is absolute: a 500\,MiB spike is as dangerous on a
larger card with the same headroom. Below $T_\mathrm{low}$ the level is RED,
below $T_\mathrm{high}$ YELLOW, and GREEN otherwise.

\paragraph{Hysteresis.} A new level is reported only once $K$ consecutive polls
have read the same side of the current level. The monitor then moves to the
level nearest the current one among those $K$ readings, the level headroom kept
throughout. A drop shorter than $K$ polls is never reported, and a clean change
is reported on its $K$th poll, within $K+1$ polls of its first reading
whatever the phase. Readings that flicker between YELLOW and RED from GREEN
report YELLOW, and RED only once RED alone has held for $K$ polls.

\paragraph{Events.} Each transition is put on a queue, which the engine drains
between decoding steps without blocking. An event carries when it happened,
the levels before and after, the headroom that settled it, and an
\textit{own/others split}: the device memory held by the engine's process and
by every other process, each by the driver's account, and how much each changed
since the transition before. The split is read at transitions only, since a
per-process query costs far more than a headroom reading. If the reader fails,
the monitor stops, and the engine records the failure rather than reading its
silence as GREEN.

\paragraph{Thresholds.} $T_\mathrm{low}$, $T_\mathrm{high}$ and $K$ are set from
the contention measured on the target machine (Section~\ref{sec:contention}) by
a fixed rule:
\begin{itemize}
\item \textbf{RED} is where the next large spike could cause an out-of-memory
failure: headroom below a spike at the P90 amplitude, rounded up to 64\,MiB.
\item \textbf{$K$} is the largest number of polls for which detection,
$(K+1) \times 50$\,ms, is no longer than the P10 rise time, so that even a fast
spike is seen before it has finished rising.
\item \textbf{YELLOW} is RED plus what a fast spike of that amplitude takes while
it is detected and a requantisation plan is applied, and no more than the
amplitude. The plan is the one that must finish before RED arrives: enough FP16
pages downgraded to INT8 to give the amplitude back.
\end{itemize}
Measured spikes give a P90 amplitude of 506\,MiB and a P10 rise time of 242\,ms,
so RED lies below 512\,MiB and $K = 3$. The rule was set before any plan had
been applied, so it estimates the plan's time at the bandwidth decoding reaches
in the experimental configuration, Qwen2.5-1.5B at 32K positions: 2.1\,GB/s. At that
rate the plan outlasts a fast spike's ramp, the margin is the whole amplitude,
and YELLOW lies below 1024\,MiB.

\subsection{The Paged Mixed-Precision Cache}
\label{sec:cache}

\paragraph{Pages and tiers.} A page holds the keys and values of $P = 32$
consecutive positions of one layer, at one of four tiers. The quantised tiers
follow KIVI \cite{liu2024kivi}: keys are quantised asymmetrically with a scale
and zero-point per (head, channel) across the page's 32 positions, and values
per (head, position). One layout serves every quantised tier, and only the
width of a code changes. Its scale metadata, 1280 bytes per page on
Qwen2.5-1.5B, does not shrink with the code. INT8, INT4 and INT2 therefore
spend 8.63, 4.63 and 2.63 \textit{effective bits} per element, and every
compression ratio in this paper is quoted from those. The page still being
filled stays at FP16, since a key channel's scale spans the whole page.

\paragraph{Memory.} Each tier has its own range of virtual addresses, reserved
for the whole context window through the virtual memory management interface
\cite{cudavmm}. Physical memory is mapped into a range a 2\,MiB granule at a
time, as pages arrive. A tier's live pages occupy its lowest slots with no holes:
freeing a page moves the tier's last page into its slot, and a granule no page
reaches into is unmapped and returned to the driver. The engine therefore holds
what its pages need, by the driver's own account. A private pool would
keep what it freed, and the monitor would read that as contention.

\paragraph{Reading.} A page is allocated at the tier it is born at once all its
positions are reserved, and is sealed, quantised once, when its last position is
stored. One attention kernel reads each page at the tier the page table records
for it, dequantising codes as it loads them, in one pass and with no workspace.
Its query tiles are aligned to pages, so a tile reads one tier, and a query reads
its own page at FP16, as a decoding query does.

\subsection{Runtime Requantisation}
\label{sec:requantisation}

A page changes tier between decoding steps, never inside a kernel launch.

\paragraph{Downgrades.} A downgrade allocates the page at the target tier while
the old page is still read, quantises it, points the page table at it, and frees
the old page. If the allocation fails, the cache is as it was.

\paragraph{The shadow.} Before a page's first downgrade, its FP16 bytes are
copied to pinned host memory, its \textit{shadow}, and kept until the cache is
released.
Every move quantises from FP16: from the page itself while it is FP16, and from
the shadow after that, never from the current codes. A page at tier $T$ is
therefore always exactly the quantisation of its FP16 rows at $T$, however many
moves it took to get there. Each tier then has one error, the one measured
offline, and errors do not compound along a page's path.

\paragraph{Upgrades.} An upgrade restores from the shadow. To FP16, the shadow
is copied back, and the page is again bit for bit what it was before its first
downgrade. Decoding the codes back up was rejected: it would give FP16's size at
the lower tier's error. The shadows of every page of Qwen2.5-1.5B at 32K
positions take about 0.9\,GiB of host memory.

\paragraph{Correctness and cost.} A cache that reached its tiers through moves
yields, bit for bit, the logits of one built at those tiers, and an upgrade to
FP16 restores them. On Qwen2.5-1.5B a move of one page of one layer takes 8 to
39\,$\mu$s at the median. The first downgrade's shadow copy is about 7\,$\mu$s
of that.

\subsection{The Attention Importance Scorer}
\label{sec:scorer}

During decoding, the attention kernel optionally writes each page's share of
each query head's attention mass. Each tile is one page and writes its partial
sum of $\exp(s - m)$ with its running maximum $m$. Once the softmax's maximum
and sum are final, the partial sums are normalised, so that a layer's pages sum
to one for each head. No second pass over the cache is needed. The mass is
averaged over a layer's query heads and folded on the device into an
exponentially weighted moving average,
\begin{equation}
  \mathrm{score}_{\ell,i} \leftarrow \alpha\, \bar{a}_{\ell,i}
    + (1 - \alpha)\, \mathrm{score}_{\ell,i}, \qquad \alpha = 0.2,
\end{equation}
where $\bar{a}_{\ell,i}$ is the mean mass on page $i$ of layer $\ell$. A
page's first observation seeds its score. The scorer folds in every fourth
step. Every step cost Qwen2.5-0.5B 0.71\% of its decode throughput, outside
noise, and every fourth step is within noise on both models. Attention sinks
receive no special protection. On both models the scorer rates the first page
highest when averaged over layers.

\subsection{The Precision Controller}
\label{sec:controller}

The controller turns a pressure level, the headroom, the scores and the
current tiers into a plan. It contains no device code.

\paragraph{A byte target.} A plan reclaims what brings headroom back above
YELLOW's threshold with a 64\,MiB margin, $T_\mathrm{high} + 64\,\mathrm{MiB} -
\text{headroom}$. A plan's size is therefore set by what the machine needs
back, not by a fixed fraction of the cache.

\paragraph{Greedy by marginal cost.} The controller repeatedly takes the
cheapest next move, a page one tier down, until the target is met. A move's
marginal cost is
\begin{equation}
  c_{\ell,i}(t \to t') = \mathrm{score}_{\ell,i} \cdot
    \frac{e(t') - e(t)}{b(t) - b(t')},
\end{equation}
where $e$ is a tier's relative mean squared error from offline round trips
and $b$ its bytes per page. With equal scores, each tier down costs more per
byte than the last, so pages go one tier at a time, breadth first. A page the
model hardly attends to goes deep first. INT2's error puts it last unless a
score outweighs it.

\paragraph{The recency floor.} The open pages and every page reaching into the
last $W = 128$ positions are never downgraded, under every policy.

\paragraph{Upgrades.} At GREEN only, pages are restored largest gain first, the
reverse of a downgrade plan, in batches within the same per-step budget. An upgrade waits at least 5\,s after the later of
the last downgrade and the end of the last pressure, and never takes headroom
below $T_\mathrm{high}$ plus 512\,MiB, one P90 spike.

\paragraph{Score sources.} Three sources of scores plug into the same planner
and meet the same byte target to within one page's move:
\begin{itemize}
\item the scorer's scores (\textit{semantic});
\item equal scores (\textit{uniform}), the main baseline, with a partial step
spread evenly across positions;
\item seeded random scores, a control.
\end{itemize}
A difference between them is a difference of allocation, not of compression.

\paragraph{The engine's reaction.} On a YELLOW event the engine applies the
plan a batch per step, each step's moves timed and held within a 20\,ms
budget. On RED it applies the whole plan at once. While the level stays YELLOW
or RED, it plans again each time the cache seals new pages. It also sizes
each prefill chunk from what the steps before it cost, a fixed part and a part
per position, so that a step takes about 0.8\,s. Where the fixed part alone
exceeds that, as on Qwen2.5-1.5B at long contexts, a step is kept to about
twice its fixed part. At GREEN, chunks stay at 512 positions.
Bounding them there too would cost 30 to 60\% of prefill throughput. If an allocation
fails outright, it makes an emergency plan for no headroom and retries the step
once. Failing that, the generation ends gracefully, \textit{exhausted}, with
the tokens it produced.

\subsection{The From-Scratch Boundary}
\label{sec:boundary}

\textit{MicroInfer} is built from scratch in the sense this work depends on:
every kernel that the research contribution touches is hand-written CUDA, and no
external inference engine --- vLLM \cite{kwon2023pagedattention}, llama.cpp
\cite{llamacpp} or TensorRT-LLM \cite{tensorrtllm} --- is used at any point. The
phrase stops at one place, the dense matrix multiplications, which call NVIDIA's
cuBLAS library \cite{cublas}. This subsection states that boundary explicitly, so
that no later result is read as implying the projections were hand-written.

\paragraph{Hand-written.} The following are CUDA kernels or host code written for
this engine:
\begin{itemize}
\item the token embedding lookup;
\item RMSNorm, over fp16 activations or over the fp32 residual stream;
\item rotary position embedding (RoPE), with its angles formed in fp64, and
tabulated once per position for the keys the cache completes;
\item the SwiGLU activation;
\item the broadcast of a projection's bias into its output rows, on which the
second precision choice below relies;
\item attention: causal scaled dot-product attention with an online softmax,
grouped-query attention, and the completion of keys cached without their
projection's bias --- over a contiguous cache, over pages, and over pages at a
quantised tier, dequantising each code as it is loaded;
\item the paged key-value cache: its page table, the stores that write it, and
the allocator beneath it, which uses the CUDA virtual memory management API so
that memory it frees returns to the driver;
\item quantisation and dequantisation of a page at INT8, INT4 and INT2;
\item greedy token selection over the logits.
\end{itemize}

\paragraph{cuBLAS.} The dense projections --- the query, key, value and output
projections of attention, the gate, up and down projections of the MLP, and the
language-model head --- call \texttt{cublasGemmEx}, through a single wrapper.
cuBLAS is a basic linear algebra library, not an inference engine: it multiplies
the matrices it is given and knows nothing of models, caches or precision tiers.

\paragraph{Why the boundary is here.} Hand-writing the matrix multiplications as
well was considered and rejected. Every latency figure this thesis reports would
inherit the gap between a hand-written GEMM and cuBLAS, and a reader could no
longer separate the overhead of the adaptive precision policy from the cost of a
slow matrix multiplication --- the very separation the systems claim rests on.
When the decision was taken the gap was estimated at two to five times. It was
then measured, in the study described last in this subsection, on the RTX 4050
Laptop GPU used throughout, at the driver's own clocks and with the desktop's
processes sharing the GPU. On the models' own projections at 512 rows, a
shared-memory-tiled kernel ran 8--28 times slower than cuBLAS and a naive one
93--267 times slower. In single-token decoding the tiled kernel ran 5--21 times
slower; those timings flatter every implementation somewhat, since a repeated
launch finds a small projection's weights still in the 24\,MiB L2 cache, which a
whole model does not fit. The measurement strengthens the decision rather than
revising it.

\paragraph{Two precision choices.} The wrapper makes two choices on which the
per-kernel correctness figures reported for the projections depend --- a
relative error of at most four units in the last place of fp16 and a mean below
one, against a float64 reference.
\begin{enumerate}
\item \textbf{fp32 accumulation, with reduced-precision reduction disallowed.}
Operands are fp16 and the computation is fp32 (\texttt{CUBLAS\_COMPUTE\_32F}).
The handle is also set to
\texttt{CUBLAS\_MATH\_DISALLOW\_REDUCED\_PRECISION\_REDUCTION}: without it,
cuBLAS may reduce the partial sums of a split-K computation in the output's
precision, which is a silent fp16 accumulation inside a call that asked for fp32.
\item \textbf{The bias folded in, so the result is rounded once.} Where a
projection carries a bias, the output rows are first seeded with it and the
multiplication adds onto them. The sum is formed in fp32 inside cuBLAS and
rounded to fp16 once, rather than rounded after the multiplication and again
after a separate addition.
\end{enumerate}
The same principle, to round as late and as seldom as possible, applies to the
projections without a bias: the output and down projections add straight into
the fp32 residual stream, and the language-model head writes fp32 logits, so
neither is rounded to fp16 at all.

\paragraph{The GEMM study.} A naive GEMM kernel and a shared-memory-tiled one were
written and profiled against cuBLAS with Nsight Compute, as a study of where
their time goes. At 512 rows the naive kernel is bound by its load and store
queue, the tiled one by shared memory, and cuBLAS by the tensor cores, which
neither hand-written kernel uses. In decoding the projection becomes a
matrix-vector product: cuBLAS switches to a kernel without tensor cores that
approaches the memory bandwidth, and the hand-written kernels stall well short of
it. Both compute the projection correctly, to the same per-kernel bound
as the engine's. The study is a learning and benchmarking artifact and nothing
more: it is not part of the inference path, and the engine's build, its import
graph and its packaged form are each tested not to reach it.

\section{Evaluation}
\label{sec:evaluation}

\subsection{Contention Characterisation}
\label{sec:spikes}
The traces of RQ1 are read by one analysis, fixed before any trace was
recorded. Free memory is sampled at 50 Hz. Its \textit{baseline} is the rolling
median of the preceding 5 s, and a \textit{spike} is free memory at least
64 MiB below the baseline for at least 100 ms; 64 MiB is an order of magnitude
above the noise of an idle desktop on the machine used, a few 2 MiB granules.
The threshold, the window and the minimum duration are parameters, and the raw
traces are kept, so every figure can be recomputed at another threshold.

Four rules make the definition hold on a real trace.
\begin{itemize}
\item \textbf{The baseline holds during a spike, for one window at most.} A
median left to roll would sink into any spike longer than half its window and
end it there. From a spike's first sample the baseline is held; a spike still
below it after a whole window is a \textit{lasting drop}, reported as not
recovered, after which the new level becomes the baseline.
\item \textbf{A spike ends only when its deficit falls below half the
threshold.} Without this hysteresis, noise on a spike near the threshold would
split it into several.
\item \textbf{A gap in the trace ends a spike.} A spike cut by a gap, or by the
end of the trace, is \textit{censored}: its duration is a lower bound, and
nothing is interpolated across the gap.
\item \textbf{A measure stays within its own spike.} Where two spikes follow too
closely for a measure to be taken, it is reported as missing rather than
stretched across both.
\end{itemize}

For each spike four measures are taken from its \textit{deficit}, the held
baseline minus free memory, with crossing times interpolated between samples.
The \textit{amplitude} is the largest deficit. The \textit{peak} is the run of
samples at or above 90\% of the amplitude around it. The \textit{rise time} runs
from the last crossing of 10\% of the amplitude before the peak to the peak's
start; the \textit{recovery} runs from the peak's end to the next crossing of
10\%, its mirror. The \textit{duration} is the time the deficit spends at or
above the threshold.

Each spike is attributed to the process most responsible for it, from the
per-process memory sampled at 5 Hz: the process whose holding gained most
between the last sample before the rise began and the samples taken during the
peak, provided the gain is at least a quarter of the amplitude, reported with
its share. Otherwise the spike names no process and records why: no sample fell
within its peak, the driver did not report the holdings, or no process gained
enough. Spikes are reported per scripted action, every action included, and as
rates per hour of recorded time for passive sessions; the counts are repeated at
thresholds of 32 and 128 MiB. Distributions of duration and recovery are drawn
from recovered spikes only, since a censored duration is a lower bound.

\subsection{Contention on the Target Machine}
\label{sec:contention}

RQ1 was measured on the machine the rest of the evaluation uses: a laptop with
an RTX 4050 Laptop GPU of 6\,GiB, under Linux with a GNOME desktop. A driver
script played one scenario of everyday actions and labelled each in the trace:
\begin{itemize}
\item a browser with 1, 5 and 10 tabs;
\item YouTube at 1080p and at 2160p;
\item a WebGL page;
\item a 2160p video in VLC;
\item VS Code.
\end{itemize}
It closed every application at the end. The model throughout is from the Qwen2.5
family \cite{qwen2024report}. A video call was part of the first
recording only; the call service then refused the scripted sign-in. The scenario was recorded five times
with \textit{MicroInfer} holding Qwen2.5-1.5B at 32K positions in FP16,
decoding continuously, and once without it: 2.2 hours of traces in all.

Table~\ref{tab:rq1} gives what the analysis of Section~\ref{sec:spikes} finds in
them, 48 spikes at the 64\,MiB threshold. At 32\,MiB there are 98 and at
128\,MiB 28.
\begin{itemize}
\item \textbf{Most contention does not go away.} 45 of the 48 spikes are
lasting drops: an application opened and kept its memory until the scenario
closed it. Only 3 recovered.
\item \textbf{Amplitude.} The median spike took 154\,MiB and the P90
506\,MiB. The largest, 567\,MiB, came from the 2160p video in VLC, whose six
spikes were all above 500\,MiB.
\item \textbf{Rise.} Spikes rise over seconds rather than milliseconds: a median
of 1.09\,s from 10\% to 90\% of the amplitude, and a P10 of 242\,ms.
\end{itemize}
Attribution named a process for 44 spikes: the browser's GPU process for most,
VLC, VS Code, the X server, and the engine itself for the five 182\,MiB steps of
its own cache growing through prefill. For the other four, either no process
sample fell within the spike's peak or no process gained a quarter of its
amplitude.

With the engine holding 32K positions, the lowest headroom seen was 377\,MiB,
and the engine ran out of memory in none of the five runs. On this machine,
then, everyday contention takes hundreds of MiB, keeps it, and brings headroom
within reach of an out-of-memory failure. It does not reach one by itself.

\subsection{Reproducing Contention}
\label{sec:simulator}

A detector cannot be tested by waiting for a browser to spike, so contention is
also reproduced on demand by a \textit{contention simulator}.
\begin{itemize}
\item \textbf{It is a process of its own,} with its own CUDA context, so that
the memory it takes is another process's to the driver and to the monitor, as
real contention is.
\item \textbf{It takes memory and launches nothing,} which isolates the variable
the evaluation studies.
\item \textbf{It takes memory through the engine's allocator,} a 2\,MiB granule
at a time, so what it gives back reaches the driver at once.
\item \textbf{It follows a schedule} of bytes taken over time. Measured on the
target machine, a change of 64\,MiB is seen by the driver 13\,ms after it is
due, and one of 1\,GiB after 208\,ms: an edge the schedule makes sheer rises as
fast as the allocator allows.
\end{itemize}

Schedules come from two sources:
\begin{itemize}
\item \textbf{Synthetic pulses:} trapezoids of a given amplitude, ramp and
plateau, played on a base that sets the headroom they start from.
\item \textbf{Replays of recorded traces.} A replay plays what the processes
other than the engine held in an RQ1 recording, sample by sample at 50\,Hz. It
does so on a base chosen so that the machine has the original's headroom
throughout, whatever the engine running beside it holds.
\end{itemize}

\subsection{Detecting Pressure}
\label{sec:detection}

RQ2 asks whether a runtime that cooperates with no scheduler can detect pressure
fast enough to act. The monitor was scored against a truth it has no part in:
the recorder's own 50\,Hz trace of headroom, with the monitor's thresholds
applied. A \textit{true RED episode} is a run of samples below RED. For each
one of at least 100\,ms, the \textit{detection latency} runs from its start to
the first RED event that reports it; an episode with none is a \textit{false
negative}. A RED event with no true RED over the polls that settled it is a
\textit{false positive}. An episode shorter than $K+1$ polls and one recorder
sample, 220\,ms, is one the monitor cannot be sure to catch: a false negative
there is counted apart.

Both kinds of contention were played while Qwen2.5-1.5B held a generation with
its monitor on:
\begin{itemize}
\item \textbf{A synthetic grid:} amplitudes of 768, 1152 and 1408\,MiB above a
base; ramps of 0, 0.25 and 1\,s; plateaus of 0.1, 0.2, 0.5 and 2\,s; three
repeats of each cell, with each gap jittered by a fraction of a poll so that
the pulses meet the polls at every phase.
\item \textbf{RQ1's five with-engine recordings, replayed,} each from the end of
the engine's prefill.
\end{itemize}

Table~\ref{tab:detection} gives the result.
\begin{itemize}
\item \textbf{Every episode that could be caught was caught, and no RED event
was false:} 84 detectable episodes, 0 false negatives, 0 false positives.
\item \textbf{Detection takes about two and a half polls after RED begins:} a
median of 114--126\,ms and at most 246\,ms. The slowest were pulses with
0.25\,s ramps, which cross RED part way up and settle below it a few samples
later.
\item \textbf{Two short episodes went unreported, by design.} Pulses with a
sheer edge and a 0.1\,s plateau leave RED episodes shorter than the three
polls the monitor needs.
\item \textbf{Replays match their originals to within tens of MiB.} The median
difference in headroom is between $-43$ and $+28$\,MiB. Because RQ1's headroom
sat close to RED, a replay shows more or fewer episodes than its original. The
monitor is scored against each replay's own truth, so the scores stand; what a
replay does not reproduce is the original's exact count.
\end{itemize}

\textbf{The monitor costs decoding nothing measurable.} With it on, decode
throughput differed from the throughput without it by $+0.17\%$ on
Qwen2.5-0.5B and $-0.32\%$ on Qwen2.5-1.5B, after a 512-token prompt. Both
differences lie within twice their standard error. A transition's own/others
split costs 0.3\,ms, once per transition.
